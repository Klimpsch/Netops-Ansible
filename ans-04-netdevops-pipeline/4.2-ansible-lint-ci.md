# 4.2 ansible-lint and CI

**Task:** set up a GitHub Actions workflow that lints every playbook on push.

## What you'll learn

| Concept | In one line |
|---|---|
| ansible-lint | Checks playbooks for mistakes, bad habits and style problems |
| Profiles | How strict the lint is: `min`, `basic`, `moderate`, `safety`, `shared`, `production` |
| `# noqa` | Tells the linter "I meant to do this" for one line |
| CI (Continuous Integration) | A server runs your checks automatically on every push |
| GitHub Actions | GitHub's built-in CI. Workflows live in `.github/workflows/` |

## Files

```
ansible-lab/
├── .ansible-lint                       <- NEW  lint settings
└── .github/
    └── workflows/
        └── ansible-lint.yml            <- NEW  the CI pipeline
```

## Part A: lint on your own computer first

Always get it passing locally before involving CI.

```bash
pip install ansible-lint
ansible-lint
```

### `.ansible-lint`: settings

```yaml
---
profile: production

exclude_paths:
  - .github/
  - collections/
  - backups/
  - configs/
  - group_vars/all/vault.yml   # encrypted; CI has no vault password
```

| Setting | Why |
|---|---|
| `profile: production` | The strictest profile. Start here: it's easier to relax rules than to tighten them later |
| `exclude_paths` | Don't lint things that aren't your code |
| `group_vars/all/vault.yml` | It's encrypted, and CI doesn't have the Vault password |

### What the linter found in this repo

When these lessons were tested, ansible-lint flagged two problems in `backup.yml`
(before the `# noqa` comments were added):

```
command-instead-of-module: git used in place of git module
backup.yml:14 Task/Handler: Stage the backups in Git

command-instead-of-module: git used in place of git module
backup.yml:20 Task/Handler: Commit (only if a config changed)
```

The linter is right that a `git` module exists, but that module can't commit. So
using `command` here is deliberate, and we tell the linter so:

```yaml
      ansible.builtin.command: git add backups  # noqa: command-instead-of-module
```

After that:

```
Passed: 0 failure(s), 0 warning(s) in 28 files processed of 30 encountered.
Profile 'production' was required, and it passed.
```

**Only use `# noqa` when you have a reason**, and name the rule. A bare `# noqa`
hides everything.

### Things ansible-lint catches that you've already been doing right

| Rule | What it wants | Where you saw it |
|---|---|---|
| `fqcn` | Full module names: `ansible.builtin.debug`, not `debug` | Every lesson |
| `name[missing]` | Every task has a `name:` | Every lesson |
| `risky-file-permissions` | `mode:` set on files and folders | 2.2 |
| `no-changed-when` | `command` tasks say when they've changed something | 4.1 |
| `var-naming[no-role-prefix]` | Role variables start with the role name | 2.4 (`baseline_...`) |
| `meta-no-info` | Roles have `meta/main.yml` | 2.4 |

Try breaking one on purpose: change `ansible.builtin.debug` to `debug` in
`gather.yml` and run `ansible-lint`.

## Part B: run it on GitHub

### `.github/workflows/ansible-lint.yml`

```yaml
name: ansible-lint

on:
  push:
  pull_request:

jobs:
  lint:
    runs-on: ubuntu-latest

    steps:
      - name: Check out the repo
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install Ansible and ansible-lint
        run: pip install ansible-core ansible-lint

      - name: Install collections
        run: ansible-galaxy collection install -r collections/requirements.yml

      - name: Run ansible-lint
        run: ansible-lint
```

| Part | What it does |
|---|---|
| `on: push` / `pull_request` | Run on every push and every pull request |
| `runs-on: ubuntu-latest` | GitHub gives you a fresh Linux machine each time |
| `actions/checkout` | Copies your repo onto that machine |
| `actions/setup-python` | Installs Python |
| `pip install ...` | Installs Ansible and the linter |
| `ansible-galaxy collection install -r ...` | Installs `cisco.ios` from your `requirements.yml` (lesson 2.4) |
| `ansible-lint` | Runs the linter. If it fails, the job fails |

The workflow **never connects to your routers.** CI only checks the code.

### Push it

```bash
git add .
git commit -m "Add ansible-lint CI"

# first time only: connect to your empty GitHub repo
git remote add origin https://github.com/<your-username>/ansible-lab.git
git branch -M main
git push -u origin main
```

**Check before pushing:** `git status` must **not** list `.vault_pass`. If it
does, check `.gitignore` from lesson 2.4.

### See the result

On GitHub, open your repo and click **Actions**. You'll see the run:

- ✅ green tick: lint passed
- ❌ red cross: click it, then open the "Run ansible-lint" step to see which file and line failed

A tick or cross also appears next to each commit.

## Try this

1. Push a broken playbook (remove a task's `name:`), watch it fail on GitHub, fix it and push again.
2. Add a syntax-check step after the lint step:
   ```yaml
         - name: Syntax check every playbook
           run: |
             for p in $(grep -l '^- name:' *.yml); do
               ansible-playbook "$p" --syntax-check || exit 1
             done
   ```
   `grep -l '^- name:'` picks only the playbooks, so `hosts.yml` and `vars.yml` are
   skipped. Syntax check doesn't decrypt Vault files, so no password is needed.
3. Protect `main`. In GitHub, go to Settings → Branches and add a rule that requires the ansible-lint check to pass before merging. Now broken playbooks can't reach `main`.
4. Add `yamllint` as another step.

## Common mistakes

| Mistake | Fix |
|---|---|
| `couldn't resolve module/action 'cisco.ios...'` in CI | The `ansible-galaxy collection install` step is missing, or `requirements.yml` is in the wrong place |
| `Decryption failed` warnings | Add `group_vars/all/vault.yml` to `exclude_paths` |
| Workflow never runs | The file must be in `.github/workflows/` (note the dot and the plural) and end in `.yml` |
| Passes locally, fails in CI | Different versions. Run `ansible-lint --version` locally, and pin versions in the `pip install` step if needed |
