# 2.3 --check, --diff and idempotency

**Task:** push the configs from lesson 2.2, and prove the second run reports zero changes.

## What you'll learn

| Concept | In one line |
|---|---|
| Idempotency | Running a playbook again changes nothing if the device is already correct |
| `--check` | Dry run: shows what *would* change, but changes nothing |
| `--diff` | Shows the actual lines that would be added or removed |
| `diff_against: running` | Tells `ios_config` what to compare against for `--diff` |
| `save_when: modified` | Only saves the config if running and startup differ |

## Why idempotency matters

```
Run 1:  device is wrong   ->  changed=1  ->  device is now right
Run 2:  device is right   ->  changed=0  ->  nothing touched
Run 3:  device is right   ->  changed=0  ->  nothing touched
```

If run 2 shows `changed`, something is off. Either the playbook sends a line the
device stores differently, or someone changed the device. A playbook that always
reports `changed` is useless for spotting drift, so **zero changes on the second run
is the test** that your automation is trustworthy.

## The files explained

### `interfaces-push.yml`

```yaml
---
- name: Push interface configs to core routers
  hosts: core_hosts
  gather_facts: false

  tasks:
    - name: Push the generated config
      cisco.ios.ios_config:
        src: "configs/{{ inventory_hostname }}.cfg"
        diff_against: running
      notify: Save config

  handlers:
    - name: Save config
      cisco.ios.ios_config:
        save_when: modified
```

| Line | What it does |
|---|---|
| `src: "configs/{{ inventory_hostname }}.cfg"` | Push the file built in 2.2 |
| `diff_against: running` | With `--diff`, compare against the running config |
| `notify: Save config` | Save only if the push changed something |
| `save_when: modified` | Smarter than a plain `write memory`. Only saves if running ≠ startup |

`ios_config` compares your lines with the running config and **only sends lines that
are missing**. That's what makes it idempotent, but only if your lines look exactly
like IOS stores them.

## Run it: the four-step routine

Use this routine for every change, not just this one.

```bash
# 1. Build the configs
ansible-playbook interfaces.yml

# 2. Dry run: what WOULD change?
ansible-playbook interfaces-push.yml --check --diff -k

# 3. Real run
ansible-playbook interfaces-push.yml --diff -k

# 4. Prove idempotency: run again, expect changed=0
ansible-playbook interfaces-push.yml -k
```

## What you should see

- **Step 2** shows `changed` and the lines that would be sent, but the router is untouched.
- **Step 3** makes the change, and the handler saves.
- **Step 4** is the goal:

```
PLAY RECAP
R1   : ok=1   changed=0   unreachable=0   failed=0
R2   : ok=1   changed=0   unreachable=0   failed=0
```

Every line the template generates already exists on R1 and R2, so you'll probably
get `changed=0` from the very first run. That's correct. `ios_config` only checks
that your lines are present, so the extra OSPF lines on the routers don't count as a difference.

## Why a playbook ISN'T idempotent: the usual suspects

| Your line | What IOS stores | Result |
|---|---|---|
| `int gi2` | `interface GigabitEthernet2` | Always `changed`. Use full names |
| `no shutdown` | *(nothing; it's the default)* | Always `changed`. Don't send default lines |
| `logging trap informational` | *(nothing; it's the default)* | Always `changed` |
| `ios_command: write memory` | n/a | Always runs. That's why the handler uses `save_when: modified` |

**Rule of thumb:** copy lines from `show running-config` exactly.

## Try this

1. Break it on purpose: add a line ` no shutdown` to the GigabitEthernet section of the template. Rebuild and push twice. Does the second run still show `changed`? Why?
2. On R2, manually change Gi2's description to `test`. Run with `--check --diff`. The diff shows exactly the drift Ansible would fix.
3. Run `ansible-playbook ntp-core.yml --check -k` from 2.1. Is it idempotent?
4. Add `-v` to see the `updates` list: the exact commands Ansible would send.

## Common mistakes

| Mistake | Fix |
|---|---|
| `--diff` shows nothing | Add `diff_against: running` to the task |
| Second run always `changed` | See "the usual suspects" table above |
| `--check` errors on a later task | A later task may rely on output from a task that didn't really run in check mode. Add `check_mode: false` to read-only tasks like `ios_command` |
